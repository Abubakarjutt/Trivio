Three implementation approaches

Pick the architecture that fits best — trade-offs shown for each

APPROACH A — Sync Pipeline
Upload ──► Server parses ──► Save + return
CSV: parse rows in tRPC mutation
PDF: extract text with pdfjs, send to Ollama
All happens in one HTTP request
Pages added:
• /statements (upload + results table)

A — Sync: simple & fast to build

Pros

  • No queue/Redis dependency
  • Fewest new files
  • Instant feedback

Cons

  • Large PDFs may timeout (30s limit)
  • Blocks HTTP thread during Ollama call
  • Hard to add progress indicator
APPROACH B — Async Queue (mirrors existing)
Upload ──► BullMQ job ──► Worker ──► Auto-save
Frontend polls /api/imports/[id]/status
Same pattern as existing Attachment extraction
StatementImport model tracks job state
Pages added:
• /statements (import history + status)
• /transactions (filterable list + edit)

B — Async Queue: consistent with codebase

Pros

  • Handles large files reliably
  • Non-blocking; retry on failure
  • Matches existing extraction pattern

Cons

  • Requires BullMQ + Redis running
  • More moving parts to build
  • Polling adds latency
APPROACH C — Hybrid (recommended ⭐)
CSV path:
CSV upload ──► Sync parse + save (instant)
PDF path:
PDF upload ──► pdfjs text extract ──► Ollama async ──► Save
SSE stream for PDF progress; instant for CSV
Pages added:
• /transactions (unified: import button + list)

C — Hybrid: best UX, no queue needed

Pros

  • CSV is instant, no spinner
  • PDF has real-time progress via SSE
  • No BullMQ/Redis dependency
  • One clean page, not two

Cons

  • Two code paths to maintain
  • SSE adds some complexity
